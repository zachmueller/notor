# Research: `write_docx` Implementation

## Summary

The originally planned `docxtemplater` HTML injection approach is **not viable** — the HTML module is a paid commercial product, which is a dealbreaker for an open-source plugin. This document describes the revised approach: a hybrid pipeline using `docx` npm (content generation) + `pizzip` (ZIP-level template grafting).

---

## Q1 — HTML Injection via docxtemplater

**Finding: Commercial/paid. Off the table.**

`docxtemplater-html-module` must be purchased from docxtemplater.com. It is not available as a free npm package. The free/open-source core of `docxtemplater` supports text substitution (`{variable}`) and looping, but not HTML/rich content injection.

**Implication**: The `{{{body}}}` HTML injection design from the high-level doc is not feasible with free npm packages. A different approach is needed for rich content injection into a `.docx` template.

---

## Q2 — Revised Template Approach: `pizzip` Body-Replacement Hybrid

Since the HTML module is commercial, we adopt a lower-level approach that achieves the same result without it.

**Core insight**: A `.docx` file is a ZIP archive. The body content lives in `word/document.xml` as an `<w:body>` element. If we generate the content using `docx` npm (which produces valid OOXML), we can extract that `<w:body>` and graft it into the template's `word/document.xml` — keeping everything else in the template untouched.

### Pipeline

```
Markdown input
    ↓ (docx npm TypeScript API)
Temporary in-memory .docx (content only, default styles)
    ↓ (pizzip: unzip temp doc)
Extract <w:body> XML
    ↓ (pizzip: unzip template)
Replace <w:body> in template's word/document.xml
    ↓ (string substitution on document.xml)
Apply {title} text replacement
    ↓ (pizzip: repack)
Output .docx
```

### What this inherits from the template

Everything except the body content is left untouched in the template ZIP:

| Template asset | Preserved? |
|----------------|-----------|
| `word/styles.xml` (style definitions) | Yes |
| `word/settings.xml` (document settings) | Yes |
| Page margins, size, orientation (`<w:sectPr>`) | Yes |
| Headers (`word/header*.xml`) | Yes |
| Footers (`word/footer*.xml`) | Yes |
| Theme, fonts, numbering | Yes |
| `word/_rels/` relationships | Yes |
| Cover page content | Replaced (it's in the body) |

### Style name matching

The content generated by `docx` npm references Word's **built-in style names** ("Heading 1" through "Heading 6", "Normal", "List Paragraph", etc.) via their stable style IDs (`Heading1`, `Normal`, etc.). Word templates that use these standard style names will render correctly. Templates with custom style names for headings/body will fall back to those styles' formatting rather than the custom variant — a reasonable degradation for v1, with custom mapping as a future enhancement.

### `{title}` substitution

Since `{title}` is a plain text replacement, it can be handled via simple string substitution on `document.xml` (and optionally on header XML files) before repacking — no need for the full `docxtemplater` runtime. Alternatively, `docxtemplater` free core (plain text tags only) can handle this cleanly.

### Libraries required

| Library | Version | License | Role |
|---------|---------|---------|------|
| `docx` | ^9.6.1 | MIT | Content generation (Markdown → OOXML) |
| `pizzip` | ^3.x | MIT | ZIP read/write for both template and output |
| `marked` | ^17.x | MIT | Markdown → HTML (used upstream of docx AST building) |

`pizzip` is already a transitive dependency of `docxtemplater` if we install it; otherwise install directly. `docxtemplater` itself is optional — the free core's only value here is clean `{title}` substitution, which simple string replacement handles equally well.

## Q3 — Markdown-to-HTML Library

**Recommendation: `marked` v17.x**

| Library | Bundle (gzip) | ESM | GFM | Notes |
|---------|---------------|-----|-----|-------|
| `marked` | ~12 KB | Yes | Built-in | Simplest API, smallest bundle |
| `remark`/`rehype` | ~25 KB | Yes (ESM-only) | Via plugin | Powerful but heavier; ESM-only complicates esbuild |
| `markdown-it` | ~44 KB | Mixed (CJS+ESM) | Via plugins | More setup required |

`marked` wins on bundle size, simplicity, and esbuild compatibility. The `remark` ecosystem's ESM-only constraint (`"type": "module"`) can complicate bundling in Obsidian's Electron/esbuild environment.

**Note on the actual pipeline**: For `write_docx`, Markdown is not converted to HTML and then to docx — instead it is parsed into a structured representation and used to build `docx` npm objects directly (paragraphs, headings, tables, etc.). `marked` or a lightweight Markdown parser is still needed to tokenize the input, but the output target is the `docx` TypeScript API, not an HTML string. An HTML intermediate may still be useful as a parsing scaffold.

## Q4 — No-Template Fallback

**Recommendation: `docx` npm package directly (no bundled template asset)**

When no template is provided, generate a clean `.docx` from scratch using the `docx` npm API. Word's built-in styles (Heading 1–6, Normal, etc.) are applied by default without any explicit style configuration.

**Against bundling a template asset**: Adding a binary `.docx` to the plugin increases bundle size and complexity without meaningful benefit — `docx` npm already produces well-formed, standard-compliant output.

**`docx` npm capability assessment** (for the standard Markdown elements we need):

| Element | `docx` API | Complexity |
|---------|-----------|------------|
| Headings H1–H6 | `HeadingLevel.HEADING_1` … `HEADING_6` | Trivial |
| Body paragraphs | `new Paragraph(text)` | Trivial |
| Bold / italic | `TextRun({ bold, italics })` | Trivial |
| Inline code | `TextRun` with monospace style | Low |
| Fenced code blocks | `Paragraph` with "Code" style or custom shading | Low |
| Bullet lists | `bullet: { level: N }` on `Paragraph` | Low |
| Numbered lists | Custom `AbstractNumbering` + `numbering` on `Paragraph` | Medium |
| Tables | `Table`, `TableRow`, `TableCell` classes | Medium |
| Horizontal rule | Custom `thematicBreak` paragraph | Low |
| Bold/italic nesting | Multiple `TextRun` children | Low |
| Blockquotes | Custom style or indented paragraph | Medium |

All elements needed for standard document output are achievable with `docx` npm at low-to-medium complexity.

## Revised Architecture Summary

```
write_docx tool
├── input: Markdown content + optional title + optional template_path
│
├── [WITH template]
│   ├── Parse Markdown → docx API objects (headings, paragraphs, tables…)
│   ├── Build temporary Document → Packer.toBuffer() → Buffer
│   ├── pizzip.unzip(tempBuffer) → extract <w:body> XML
│   ├── pizzip.unzip(templateBuffer) → load template ZIP
│   ├── Replace <w:body> in template's word/document.xml
│   ├── Apply {title} substitution in document.xml + header XML files
│   ├── pizzip.generate() → output Buffer
│   └── fs.writeFile(outputPath, buffer)
│
└── [WITHOUT template]
    ├── Parse Markdown → docx API objects
    ├── Build Document with default styles
    ├── Packer.toBuffer() → Buffer
    └── fs.writeFile(outputPath, buffer)
```

**npm dependencies to add**: `docx`, `pizzip`, `marked`

## Open Questions for Spec

1. **Style name mapping configuration**: When a user's template uses custom style names, the content will still render but won't apply those custom styles. A future enhancement could allow a per-template or global config mapping `h1 → "My Heading 1"` etc. This is out of scope for v1.

2. **`{title}` scope**: Should `{title}` substitution scan only `word/document.xml`, or also header/footer XML files? For templates where the title appears in a running header (common), headers must be included. Recommendation: scan all XML files in the ZIP for `{title}`.

3. **Section properties (`<w:sectPr>`)**: The `<w:sectPr>` block (page layout, margins, headers/footers links) lives at the end of `<w:body>`. When replacing the body, we must preserve the template's `<w:sectPr>` rather than using the one from the generated temp doc. This requires extracting and reinserting it during the body-replacement step.
